## 1. 產品摘要

Service Frontdesk Platform 是一個**接在商戶現有系統前面的 AI 客戶端 / AI 前台**。

它不要求牙科診所、寵物美容店、清潔公司、汽車維修店或美容店先換掉現有 CMS、CRM、日曆、Excel 或紙本流程，而是先處理最消耗人手、也最容易標準化的前台工作：

- WhatsApp / Web 常見問題即時回覆；
- 預約確認、改期、取消與提醒；
- 高優先級訊息標記並通知員工；
- 對話摘要與人工接管；
- 日曆及既有系統的輕量同步；
- **用手機拍舊系統畫面、紙張、客戶卡、預約簿或表格，自動擷取重要資料，經人手核對後保存到通訊錄、客戶庫或原有系統。**

平台採用 **Service Frontdesk Core + Vertical Pack（行業包）** 架構。同一個核心可透過行業包切換牙科、寵物、美容、汽車、家居服務等行業的術語、服務項目、FAQ、風險規則、跟進週期與外部整合目標。

核心產品原則是：

> **讓商戶先獲得自動化收益，再逐步深化整合，而不是先做昂貴、漫長的系統更換。**

## 2. 背景與問題

### 2.1 現況

大量中小型服務商戶已經「有系統」，但實際工作仍分散在：

- WhatsApp；
- 電話；
- Google Calendar / Outlook；
- 行業專用 CMS；
- Excel / Google Sheets；
- 紙本客戶卡、預約簿、維修記錄；
- 員工私人通訊錄或手寫備註。

真正的成本往往不是缺少另一套大型管理系統，而是：

1. 客戶重複問同一批問題；
2. 預約確認、改期、取消需要人工來回處理；
3. 沒有人持續做召回 / 跟進；
4. WhatsApp 對話太長，前台要重新讀上下文；
5. 舊資料搬遷成本高，商戶因而不願換工具；
6. 新系統「理論上功能很多」，但導入與學習成本太高。

### 2.2 產品機會

如果新系統可以做到：

> **「不用換原有系統；先把 WhatsApp 接上。舊資料甚至可以拿手機拍一下，確認後就導入。」**

導入阻力會顯著低於傳統 SaaS 的完整遷移流程。

因此，本產品的核心競爭力不應只是「AI 回覆」，而是：

- **低門檻導入；**
- **與舊系統共存；**
- **人機協作而不是全自動冒險；**
- **一個核心快速複製到多個服務行業。**

## 3. 產品定位與邊界

### 3.1 是什麼

Service Frontdesk Platform 是：

- AI 前台；
- 客戶溝通層；
- Booking / 提醒 / 跟進執行層；
- 舊資料智能遷移層；
- 多系統 Adapter（適配器）層；
- 人工處理前的上下文壓縮與分流層。

### 3.2 不是什麼

第一階段**不是**：

- 完整替代牙科 CMS / 汽車維修 ERP / 美容 POS；
- 自動醫療診斷工具；
- 自動判斷車輛是否可安全駕駛的系統；
- 自動提供危險水電維修操作指引的工具；
- 以「必須自己從零訓練一個大模型」為前置條件的 AI 研究項目。

### 3.3 核心產品原則

1. **共存優先於替換。**
2. **易上手優先於功能堆疊。**
3. **低風險流程自動化，高風險流程人工接管。**
4. **公開 / 成熟模型 Provider 優先，訓練模型需由真實資料缺口驅動。**
5. **新行業以 Vertical Pack 擴展，不複製 Core。**
6. **所有重要資料寫入前，必須有明確來源與可核對路徑。**

## 4. 目標用戶與角色

### 4.1 商戶類型

首批目標：

- 牙科診所；
- 寵物美容 / 寄養；
- 清潔 / 家居服務 / 水電；
- 汽車維修 / 保養；
- 美容 / 護理服務。

後續可延伸至其他以「客戶溝通 + 預約 / 派單 + 提醒 + 跟進」為核心的小型服務業。

### 4.2 角色

**商戶負責人 / 店主**
- 設定服務、規則、FAQ、員工權限；
- 查看 Agent 成效；
- 批准高風險操作；
- 管理整合與資料來源。

**前台 / 行政人員**
- 處理需要人工介入的對話；
- 核對智能導入資料；
- 管理預約與提醒；
- 查看每日待辦與摘要。

**服務人員 / 技師 / 美容師 / 醫生等**
- 查看與自己相關的 Booking / 工作時段；
- 接收需要跟進的高優先級事件；
- 第一階段不要求使用完整後台。

**客戶**
- 使用 WhatsApp / Web 等熟悉渠道；
- 查詢、確認、改期、取消；
- 接收提醒；
- 不需要理解 Agent 或後台系統。

## 5. 通用領域模型

Core 不以「病人 / 醫生 / 診所」作為唯一模型，而採用：

```text
Tenant       商戶
Customer     客戶
Subject      服務對象（可選）
Service      服務項目
Resource     服務資源 / 人員 / 工位
Booking      預約 / 上門 / 入廠時段
Conversation 對話
Follow-up    跟進 / 召回
Integration  外部系統連接
```

### 5.1 行業映射例子

| 行業 | Customer | Subject | Resource | Booking |
|---|---|---|---|---|
| 牙科 | 病人 | 病人 | 醫生 / 診室 | 到診預約 |
| 寵物美容 | 寵物主人 | 寵物 | 美容師 / 房間 | 美容 / 寄養預約 |
| 汽車維修 | 車主 | 車輛 | 技師 / 工位 | 入廠時段 |
| 家居服務 | 住戶 | 地址 / 物業 | 師傅 | 上門時段 |
| 美容 | 顧客 | 顧客 | 美容師 / 房間 | 護理預約 |

## 6. 產品架構：Core + Vertical Pack

### 6.1 Service Frontdesk Core

所有行業共用：

- Messaging Adapter；
- FAQ 引擎；
- Booking 引擎；
- 提醒引擎；
- Follow-up / Recall 引擎；
- 對話摘要；
- 人工接管；
- 風險 / 升級機制；
- 智能資料導入；
- 多租戶；
- 權限與審計；
- Integration Adapter。

### 6.2 Vertical Pack

每個行業包可定義：

- UI 名稱與角色稱謂；
- 服務項目；
- FAQ 模板；
- 高優先級升級關鍵詞；
- 受限專業問題規則；
- Booking 規則；
- Follow-up / Recall 規則；
- 特有服務對象欄位；
- 目標外部系統與整合能力。

### 6.3 權限原則

Vertical Pack 是**配置，不是授權**。

它可以說「這個行業要看哪些欄位、哪些問題要轉人工」，但不能賦予 Agent 新的專業判斷權。

## 7. 第一階段核心功能

### 7.1 WhatsApp / Web FAQ 即時回覆

**需求**
- 只使用商戶明確授權的 FAQ；
- 支援營業時間、地址、服務流程、預約政策、付款方式等行政問題；
- 未命中時不猜；
- 受限專業問題轉人工。

**主要流程**

```text
客戶訊息
→ 高優先級升級規則
→ 受限專業問題檢查
→ Booking 意圖
→ 授權 FAQ
→ 人工接管
```

### 7.2 Booking 提醒與一鍵操作

提醒可提供：

- 確認；
- 改期；
- 取消。

改期流程：

```text
按「改期」
→ 查詢可用時段
→ 顯示候選時間
→ 客戶選擇
→ 寫回 Booking Adapter
→ 同步日曆 / 外部系統
→ 回覆確認
```

接近服務時間的改動可依商戶規則轉人工。

### 7.3 高優先級訊息升級

不同行業有不同規則，例如：

- 牙科：流血不止、呼吸困難等；
- 家居：漏電、冒煙、煤氣味等；
- 汽車：需要人工判斷是否可安全繼續駕駛的情況；
- 寵物：涉及疾病、用藥等專業判斷。

系統只負責：

> **識別「需要立即由人看」；不代替專業人員作結論。**

### 7.4 簡單日曆同步

第一階段優先實現通用日曆橋接。

Booking 成功後：
- 建立 / 更新日曆事件；
- 取消時同步取消；
- 同步失敗需要顯式報錯並進入人工檢查隊列。

### 7.5 對話摘要

前台不用重讀完整對話，可看到：

- 客戶意圖；
- 已完成動作；
- 仍待確認事項；
- 是否命中升級規則；
- 下一步建議。

摘要不應生成沒有來源的專業判斷。

## 8. 智能遷移：手機拍照導入舊系統資料

這是本產品「易上手」策略的核心功能之一。

### 8.1 使用場景

商戶可直接：

- 拍舊 CMS 客戶頁；
- 拍 Excel / 舊軟件螢幕；
- 拍紙本客戶卡；
- 拍預約簿；
- 上傳截圖；
- 上傳 PDF / 掃描件。

### 8.2 目標體驗

```text
[拍照 / 上傳]
      ↓
自動識別版面與文字
      ↓
擷取姓名 / 電話 / 日期 / 服務 / 備註等欄位
      ↓
映射到目前行業的資料結構
      ↓
查找重複客戶 / 衝突資料
      ↓
人手核對
      ↓
[確認並保存]
      ↓
通訊錄 / 客戶庫 / 原有 CMS / CRM
```

### 8.3 OCR / VLM Provider Pool

第一版不綁定單一模型。

系統維持 `Document Intelligence Provider Pool`，可按不同資料類型選用或組合：

- 純文字 OCR；
- 相機拍攝文件解析；
- 複雜版面 VLM；
- 表格 / 表單解析；
- 結構化資訊抽取。

Provider 選擇標準包括：

- 關鍵字段準確率；
- 中文 / 英文混排；
- 手機拍攝與屏攝魯棒性；
- 表格、版面、異形區域能力；
- 延遲；
- GPU / CPU 資源；
- 部署方式；
- 授權條款；
- 成本。

### 8.4 結構化輸出

模型輸出不能只是一段 OCR 文字。

例：

```json
{
  "customer_name": "陳大文",
  "phone": "91234567",
  "last_service": "洗牙",
  "last_service_date": "2026-08-17",
  "followup_rule": "6_months",
  "preferred_channel": "whatsapp"
}
```

每個欄位應盡可能附帶：

- `value`；
- `confidence / status`；
- 來源圖片；
- 來源區域 / bounding region；
- Provider；
- 原始文字。

### 8.5 人工核對 UI

核對頁應採「原圖 + 欄位」並排：

```text
原圖                         擷取結果
------------------          ------------------
[舊系統截圖]                 姓名  陳大文      ✓
                             電話  9123 4567   ✓
                             日期  2026-08-17  ⚠
                             服務  洗牙        ✓

                             [確認並保存]
```

規則：

- 未核對資料不得直接成為正式客戶資料；
- 低置信 / 衝突字段必須突出顯示；
- 可一鍵查看字段在原圖中的來源；
- 可修改後再確認；
- 人工修正可進入匿名化 / 合規的訓練資料候選池。

### 8.6 去重與合併

寫入前可按：

- 電話；
- 姓名 + 電話尾碼；
- 外部系統 ID；
- Email；
- 行業特有識別欄位；

生成候選重複項。

不應在高不確定情況下自動合併。

### 8.7 模型訓練策略

首版原則：

> **先 Benchmark 公開 / 成熟 Provider，後決定是否微調；從零訓練不是第一階段依賴。**

當真實商戶使用後，系統會自然累積：

```text
圖片
+ 模型原預測
+ 人工修正
+ 最終確認結果
```

只有當這些真實資料顯示公開模型存在穩定、可量化的領域缺口時，才考慮：

1. Prompt / Schema 優化；
2. 後處理 / 規則模型；
3. 小模型微調；
4. 最後才是更深度的自研訓練。

## 9. Follow-up / Recall 跟進引擎

同一引擎由 Vertical Pack 提供週期與模板：

| 行業 | 例子 |
|---|---|
| 牙科 | 6 / 12 個月洗牙召回 |
| 寵物 | 4–8 週美容提醒 |
| 美容 | 30 / 60 日護理回訪 |
| 汽車 | 里程 / 月份保養提醒 |
| 家居 | 每週 / 每月清潔服務 |

流程：

```text
歷史服務完成
→ 產生下一次 Follow-up due date
→ 到期建立任務
→ WhatsApp / Web 通知
→ 客戶回覆
→ 直接進入 Booking 流程
```

## 10. 外部系統整合策略

### 10.1 Adapter First

Core 只依賴通用介面：

- `MessagingAdapter`
- `BookingSystemAdapter`
- `CalendarAdapter`
- `Customer/Contact Adapter`
- `Document Intelligence Provider`
- `Writeback Adapter`

### 10.2 整合層級

**Level 0：無整合**
- FAQ + 人工通知；
- 商戶仍手動更新原系統。

**Level 1：日曆 / 通訊錄橋接**
- 最快落地；
- 適合第一批試點。

**Level 2：API / CSV / 官方匯入匯出**
- 與現有 CMS/CRM 有限雙向同步。

**Level 3：深度原生整合**
- 只在取得正式接口、授權、文件或現場驗證後實現。

未取得證據前，不宣稱任何第三方系統已支援某 API。

## 11. 數據、私隱與安全

### 11.1 多租戶

- 每個 Tenant 的資料、Session、Booking、對話、規則、審計獨立；
- 所有服務端操作必須驗證 tenant boundary；
- 不能依靠 UI 隱藏實現隔離。

### 11.2 最小必要資料

AI 執行流程只取得完成任務所需資料。

例如：
- 發提醒不需要完整歷史檔案；
- FAQ 不需要客戶敏感資料；
- 模型解析資料只保留核對與寫入所需內容。

### 11.3 Human-in-the-loop

必須人工介入：

- 高優先級升級訊息；
- 受限專業問題；
- 低置信 / 衝突資料導入；
- 高風險 Agent 寫操作；
- 未知流程；
- 權限不足。

### 11.4 審計

關鍵事件需記錄：

- 誰 / 哪個 Agent；
- 何時；
- 讀取 / 修改了什麼；
- 使用哪個 Provider；
- 為何自動執行 / 為何轉人工；
- 人工核對結果。

## 12. 核心用戶流程

### 12.1 新商戶快速上手

```text
建立 Tenant
→ 選行業 Pack
→ 設定營業時間 / 服務
→ 匯入或拍照導入舊客戶資料
→ 人工核對
→ 連 WhatsApp / 日曆
→ 啟用 FAQ + 提醒
```

目標：**在不完成深度 CMS 整合的情況下，先產生可用價值。**

### 12.2 客戶改期

```text
收到提醒
→ 按改期
→ 顯示空檔
→ 選時段
→ Booking Adapter 更新
→ 日曆同步
→ 客戶收到確認
```

### 12.3 舊資料拍照遷移

```text
前台拍一張舊系統畫面
→ 自動抽字段
→ 系統提示疑似重複客戶
→ 前台修正日期
→ 確認
→ 寫入客戶庫 / 通訊錄
```

## 13. 非功能需求

### 13.1 易用性

- Mobile-first（手機優先）；
- 核心操作避免要求使用者理解 AI / OCR / VLM；
- 「拍照導入」應是一級入口，而不是隱藏在進階設定；
- 所有需要人工處理的事件統一進「待人工」工作台。

### 13.2 性能目標（Pilot）

這些是試點目標，不是已達成聲明：

- FAQ 常規回覆：P95 < 4 秒；
- Booking 按鈕操作：P95 < 5 秒（不含第三方系統延遲）；
- 單張圖片第一輪字段提取：目標 < 10 秒；
- 手機上傳後必須立即顯示處理狀態；
- 第三方系統失敗不可讓前端無限等待。

### 13.3 可替換性

- OCR/VLM Provider 可替換；
- Messaging Provider 可替換；
- Calendar / Booking Provider 可替換；
- Vertical Pack 不可 fork Core 才能工作。

## 14. Pilot 關鍵指標

### 14.1 商戶價值

- 每週被 AI 自動處理的重複對話數；
- 人工閱讀對話時間下降比例；
- 預約未確認數下降；
- 改期 / 取消平均處理時間；
- Follow-up 轉換為 Booking 的比例；
- 新商戶首次獲得價值所需時間（Time to First Value）。

### 14.2 智能導入

必須按字段計算，而不是只看整頁 OCR 分數：

- 姓名字段準確率；
- 電話字段準確率；
- 日期字段準確率；
- 服務項目映射準確率；
- 低置信字段召回率；
- 人工修正率；
- 重複客戶誤合併率（應接近 0）；
- 平均每筆資料核對時間。

### 14.3 自動化安全性

- 未授權 FAQ 自動回答率 = 0；
- 跨租戶操作成功率 = 0；
- 高風險 / 受限問題錯誤自動執行率 = 0；
- 未人工確認的智能導入資料寫入正式資料庫數 = 0。

---

## 15. 第一階段驗收標準

第一階段可進入真實商戶 Pilot，至少需要：

1. WhatsApp 或 Web 一個真實渠道完成入站 / 出站；
2. 授權 FAQ 可自動回覆；
3. Booking 確認 / 改期 / 取消完成閉環；
4. 至少一個日曆或 Booking Adapter 真實可用；
5. 高優先級升級可通知員工；
6. 人工接管不丟失上下文；
7. 拍照導入能輸出結構化字段；
8. 拍照導入必須有人手核對介面；
9. 確認後能至少寫入一個真實目標（平台客戶庫 / 通訊錄 / CSV / 外部系統之一）；
10. 多租戶與審計基本邊界成立；
11. 所有未驗證第三方能力在 UI / 文件中明確標記；
12. 相關流程有定向測試，不要求每次提交都跑完整回歸。

## 16. Roadmap

### Phase 1 — AI Frontdesk + Easy Onboarding

- WhatsApp / Web FAQ；
- Booking 提醒、確認、改期、取消；
- 高優先級升級；
- 日曆同步；
- 對話摘要；
- **手機拍照智能導入 + 人工核對 + 客戶資料寫入。**

### Phase 2 — Revenue / Retention Automation

- Follow-up / Recall；
- 未回覆自動跟進；
- 行業特有召回；
- 更深 CRM / CMS Adapter；
- 數據導入批處理；
- 重複資料治理。

### Phase 3 — Vertical Factory

- 由 DWAC 根據行業需求生成 Vertical Pack 候選工件；
- 自動產生 FAQ、流程、字段 Schema、測試、Demo 資料、銷售說明；
- 通過人工 / 驗收門後上線；
- 形成「一個行業成功 → 快速複製下一行業」的產品工廠。

### Phase 4 — Domain Model Optimization（可選）

只在真實數據證明有需要時：

- OCR/VLM 微調；
- 小型字段抽取模型；
- 行業特有去重 / 映射模型；
- 本地端模型部署。

---

## 17. 非目標

v0.1 不承諾：

- 取代所有行業 CMS / ERP；
- 全自動處理所有客戶問題；
- 無人工核對的大規模舊資料遷移；
- 為所有第三方系統提供即插即用 API；
- 從零訓練通用 OCR / VLM；
- 以 AI 代替需要專業牌照或責任判斷的人員。

## 18. 主要風險與待驗證假設

### R1. 舊系統拍照資料質量差異很大

**應對：** Provider Pool + 圖像品質檢測 + 低置信 abstain（拒答 / 待核對）。

### R2. 不同行業字段差異超出現有通用模型

**應對：** Subject Schema 與 Vertical Pack 擴展，不直接污染 Core。

### R3. 商戶沒有 API

**應對：** 日曆、CSV、通訊錄、人工 bridge 先落地；深度整合後置。

### R4. 過度自動化造成責任風險

**應對：** RCL / Policy Gate、closed operation set、人手批准、審計。

### R5. 「自己訓練模型」消耗資源但沒有產品收益

**應對：** 先以真實 Pilot Benchmark 證明公開 Provider 的持續缺口，再決定微調 / 訓練。

### R6. 通用平台變成「什麼都能做但什麼都不深」

**應對：** Core 通用、Vertical Pack 深化；每次只選一個行業做完整閉環後再複製。

## 20. 當前產品判斷

最合理的首個真實 Pilot 不是「把所有行業都做完」，而是：

1. 選一個有真實商戶的行業；
2. 完成 WhatsApp + Booking + 智能拍照導入三個核心閉環；
3. 量化節省的人手時間與導入成本；
4. 把成功流程固化為 Vertical Pack；
5. 再複製至第二個行業。

**產品是否成功，不以功能數量衡量，而以「商戶多久能開始用、多少重複工作被接走、多少舊資料能低成本搬進來」衡量。**
